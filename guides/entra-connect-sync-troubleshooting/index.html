Guide

Diagnosing Entra Connect Sync Issues

In a hybrid setup, accounts are mastered on-premises and synced to Entra ID by Entra Connect. When a user is missing in the cloud, or an attribute change on-premises never appears, the cause is almost always sync scope, a matching conflict, or the source anchor. This guide works through them in order.

Commands run in one of three places, called out per step: a domain controller, the Entra Connect server, or any machine with the Microsoft Graph PowerShell module. Names like corp.local and jane.doe@example.co.uk are examples.

Step 1

Confirm the Symptom

Decide which case you have: the object is missing in the cloud, or it exists but an attribute is stale. Check the cloud side from any machine with the Graph module. 

Connect-MgGraph -Scopes User.Read.All
Get-MgUser -Filter "userPrincipalName eq 'jane.doe@example.co.uk'" -Property OnPremisesSyncEnabled,OnPremisesImmutableId,UserPrincipalName

No result: the object is not syncing at all. Continue to scope and matching.

Result with OnPremisesSyncEnabled empty: a cloud-only object exists and may be blocking the match.

Result present but attribute old: the object syncs; the issue is a filtered attribute or a pending cycle.

Step 2

Check Sync Scope

Entra Connect only syncs objects inside its configured OUs and groups. A user in an unselected OU never syncs. On the Entra Connect server, review the filtering configuration (Entra Connect wizard > Domain and OU filtering), and confirm the user's OU is selected.

Step 3

Check for Sync Errors

Look for a duplicate-attribute error, the most common blocker. In the portal go to Identity > Hybrid management > Microsoft Entra Connect > Connect Sync > Health > Sync errors. A "Duplicate Attribute" entry confirms a UPN or proxyAddress clash with an existing cloud object.

Step 4

Trace the Single Object

On the Entra Connect server, trace just this object to see whether it is in scope, which rules apply, and where it stops. Needs Entra Connect 2.x or later. 

Invoke-ADSyncSingleObjectSync -DistinguishedName "CN=Jane Doe,OU=Users,OU=London,DC=corp,DC=local" | Out-File C:\Temp\jdoe-sync.json

On older builds, use the Synchronization Service Manager > Connectors > AD connector > Search Connector Space instead.

Step 5

Check the Source Anchor

Entra Connect matches on the source anchor (mS-DS-ConsistencyGuid or objectGUID). If the on-premises anchor does not match the cloud ImmutableId, the object will not join. On a domain controller, read the on-prem value and compare it to the cloud value. 

$onprem = [Convert]::ToBase64String((Get-ADUser jane.doe -Properties 'mS-DS-ConsistencyGuid').'mS-DS-ConsistencyGuid')
$onprem
$onprem -ceq "PASTE-CLOUD-IMMUTABLEID=="

True: the anchors match, so the anchor is not the problem. Read the Step 4 trace instead.

False: the anchors differ. Stamp the on-prem value onto the cloud object (Step 6). Use -ceq, not -eq, because base64 is case-sensitive.

Confirm which attribute Entra Connect actually uses as its anchor, on the Entra Connect server: 

(Get-ADSyncGlobalSettings).Parameters | Where Name -eq "Microsoft.SynchronizationOption.AnchorAttribute" | Select Value

Step 6

Resolve the Conflict

Stale cloud object blocking a soft match: delete the cloud-only object and remove it from the recycle bin, then sync. A cloud account holding an admin role blocks soft match by default, which is why cloud-only admin accounts should stay separate from synced identities.

Anchor mismatch: hard match by stamping the on-prem anchor onto the cloud object with Update-MgUser -UserId ... -OnPremisesImmutableId "..." from a machine with the Graph module.

Step 7

Force a Sync and Verify

On the Entra Connect server, run a delta cycle, then confirm in the portal. 

Start-ADSyncSyncCycle -PolicyType Delta

Verify: the user in the portal shows "On-premises sync enabled: Yes" and the expected UPN and attributes.

If still missing: re-read the Step 4 trace for a stale join to a deleted duplicate, which needs a full cycle (-PolicyType Initial) to clear.

Why It Matters

Security Angle

Hybrid identity is the seam between on-premises and cloud, and it is a target. Keep cloud admin accounts cloud-only so a compromised on-prem account cannot soft-match into a privileged cloud identity. Anchor on mS-DS-ConsistencyGuid so a rebuilt or moved account keeps its cloud identity instead of creating a duplicate. Watch Entra Connect Health for repeated duplicate-attribute or export errors, which can indicate account tampering as well as misconfiguration.
